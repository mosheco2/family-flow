בקרת גישה, בעלות ומבנה כללי של מודול הספורט

מטרה וטריגר
כל נתיבי /api/sport/* (server.js:29223–30907) ו-/api/ai/sport/training-plan משרתים שלושה צרכנים: מסך BIZ (business-app.js:44756–50122, 57388–57450, 60126–60344), חנות ציבורית (storefront-sport.html, storefront.html מורשת, storefront-btype.js, sc-auth.js), ואפליקציית המשפחה (app.js:14127–14141).
תנאים ואימותים
  • אף נתיב ספורט אינו מוגן ב-middleware (mw: [] לכל הנתיבים ב-api.json; אין verifyBiz/verifyFamily). אין בדיקת בעלות: groupId נלקח מה-body/params כפי שהוא, ונתיבים לפי :id (חבר, שיעור, מאמן, תור) פועלים על כל רשומה בכל עסק.
  • אין gating לפי business_type או מודול בצד שרת. ה-gating היחיד הוא בצד לקוח: דשבורד ספורט מוצג רק ל-role==='ADMIN' ו-business_type==='sport' (business-app.js:5628), ומנהל סניף בעסק ספורט מקבל את אותו דשבורד (business-app.js:39856).
  • יומן הביקורת הגלובלי (server.js:121–144) רושם רק בקשות עם req.bizAuth — ולכן אף פעולת ספורט לא נרשמת בו אוטומטית; רישום ידני קיים רק ל-FREEZE/CANCEL/DELETE (ראו תהליכים).
  • מודולי BIZ לסוג ספורט: ['feed','calendar','pos','sales','customers','members','timeclock','cashflow','tasks','equipment','shifts','biz-ads','reports'] (business-app.js:37536). מסכי הספורט עצמם אינם טאבים אלא מודאל #sport-modal בתוך content-feed (_ensureSportModal, business-app.js:45591).
שלבי עיבוד
  1. הסכמה נוצרת באתחול (server.js:1654–1863) ב-CREATE TABLE IF NOT EXISTS/ALTER … ADD COLUMN IF NOT EXISTS עטופים ב-try/catch שקט.
  2. אין טרנזקציות באף נתיב ספורט — כל כתיבה היא pool.query נפרד.
חישובים
קבוע יחיד ברמת מודול: SPORT_MEMBERSHIP_EXPIRING_SOON_DAYS = 14 (server.js:29226). תאריכי DATE של pg מוחזרים כאובייקט Date של JS (אין setTypeParser בקוד) — משמעות לחישובי זמן מתועדת בפערים בתהליכים הרלוונטיים.
תופעות לוואי
פונקציות עזר משותפות: logBizIncome (server.js:4201, כותב transactions type=income, category='sales', משויך ל-ADMIN הראשון); logBizExpense (server.js:4213); upsertStoreCustomer (server.js:7393 — מאחד כרטיס store_customers לפי טלפון, יוצר/מקשר member_business_links אם יש משפחה ב-WEFLOWZ); _sendMemberBizNotif (server.js:30937 — הודעה ב-alert_notifications עם trigger_type='business_update', דה-דופליקציה לפי (group_id, reference_key)); logBizAction (server.js:4160, biz_audit_log).
ממשק
ניתוב פעולות מהירות דרך עטיפות שרשרת של window.rdAction (business-app.js:45579, 46485, 48292, 48619, 49511, 60126): sport-checkin, sport-members, sport-add-member, sport-membership-types, sport-schedule, sport-alerts, sport-reports, sport-waivers, sport-trainers, sport-leads, sport-oneflow, sport-inbox, sport-ai, sport-appointments. פונקציות רבות מוגדרות מחדש מספר פעמים; ההגדרה האחרונה בקובץ היא הפעילה (למשל showSportSchedule 7 פעמים, האחרונה business-app.js:49886; _sportMemberCard 4 הצהרות function, האחרונה business-app.js:48306).
פערים
היעדר אימות ובעלות בכל המודול: כל אחד יכול לקרוא רשימות חברים כולל טלפונים (GET /api/sport/members/:groupId — ש-storefront.html:4993 אף קורא מהחנות הציבורית), למחוק חברים/שיעורים/מאמנים, ולסמן שכר כשולם.

ניהול סוגי מנויים (sport_membership_types)

מטרה וטריגר
מנהל העסק מגדיר מסלולי מנוי (מחיר, משך, מכסת כניסות). מסך יחיד: טאב "מכירות" ← קטלוג (renderSportSalesCatalogView, business-app.js:45208). showSportMembershipTypes רק מנווט לשם (business-app.js:45201). גם נזרע אוטומטית בויזארד AI (server.js:5552–5562).
תנאים ואימותים
  • לקוח: שם חובה — "יש להזין שם" (business-app.js:45360, 45399). מחיר parseFloat||0; כניסות parseInt||null.
  • שרת POST (server.js:29263): ללא אימות; type||'monthly', price parseFloat||0, color||'indigo', תמיד is_active=true,is_public=true.
  • שרת PUT (server.js:29281): ללא אימות; duration_days נגזר מ-durationMap[type] ולא מהקלט.
  • DELETE (server.js:29274): מחיקה פיזית; FK ב-sport_memberships.membership_type_id הוא ON DELETE SET NULL (server.js:1674).
שלבי עיבוד
  1. GET /membership-types/:groupId — כל הסוגים (כולל לא פעילים/לא ציבוריים) ממוינים לפי מחיר עולה (server.js:29258).
  2. POST — INSERT יחיד.
  3. PUT — UPDATE של name,type,price,duration_days,sessions,updated_at.
  4. DELETE — DELETE יחיד; מנויים קיימים נשארים עם membership_type_id=NULL.
חישובים
durationMap = { monthly:30, yearly:365, punch_card:null, day_pass:1, pt_sessions:null } (לקוח business-app.js:45361 נשלח כ-durationDays ב-POST; שרת server.js:29284 ב-PUT). בויזארד: duration_days = mt.duration_days||30, price = mt.price||200, color = mt.color||'#6366f1' (server.js:5558–5559).
מכונת מצבים
שדות בוליאניים is_active/is_public — אין UI או נתיב לשינוים (תמיד true). הנתיב הציבורי מסנן לפיהם (server.js:30057).
ממשק
טופס הוספה מוזרק (business-app.js:45236), עריכה inline לכל שורה (business-app.js:45291), תוויות סוג: {monthly:'חודשי', yearly:'שנתי', punch_card:'כרטיסייה', day_pass:'יומי', pt_sessions:'PT'} (business-app.js:45269). לצידם מוצגים מוצרי קטלוג רגילים (/api/store/catalog) וקיצור ל"כללי הרשמה לשיעורים".
פערים
  • PUT מעדכן updated_at, אך העמודה לא קיימת בטבלה (server.js:1655–1666, אין ALTER) — סביר שכל עריכת סוג מנוי נכשלת בשגיאת SQL.
  • פרומפט ה-AI בויזארד מציע סוג class_pack (server.js:5264) שאינו במפת המשכים/תוויות; כרטיסייה מקבלת ברירת מחדל 30 יום אם ה-AI לא החזיר duration_days.
  • הוספות הויזארד נעשות ב-pool.query בתוך פונקציה שפתחה טרנזקציה על client (server.js:5452, 5555) — לא חלק מהטרנזקציה.

תופעות לוואי

ממשק

פערים

הוספת חבר חדש (BIZ)

מטרה וטריגר
מנהל רושם חבר חדש. מסך showSportAddMember (business-app.js:45091; עטיפה שמוסיפה תאריך לידה/מגדר business-app.js:48358) ← _sportSubmitNewMember (גרסה פעילה business-app.js:48387). גם מהמרת ליד (business-app.js:48606).
תנאים ואימותים
  • לקוח: שם חובה "יש להזין שם"; סוג מנוי חובה "יש לבחור סוג מנוי" (business-app.js:48399–48400). אם אין סוגי מנוי — מוצג קישור להוספה ואין select.
  • שרת (server.js:29348): ללא אימות שדות. מקבל name|memberName, phone|memberPhone, email|memberEmail. סוג מנוי לא קיים ⇒ המנוי נוצר ללא תאריך סיום ומכסה.
שלבי עיבוד
  1. SELECT סוג המנוי.
  2. חישוב end_date ו-sessions_total.
  3. INSERT sport_memberships (status ברירת מחדל 'active', start_date = startDate || היום, notes||'', date_of_birth, gender, id_number).
  4. אם paymentAmount > 0: INSERT sport_payments (payment_method||'cash', notes='הצטרפות מנוי חדש') ואז logBizIncome עם תיאור "הצטרפות מנוי חדש — שם" (server.js:29367–29371).
  5. upsertStoreCustomer (ללא await) עם notes "חבר מועדון: {שם הסוג}".
  6. לקוח: אם הגיע מהמרת ליד — PUT /api/sport/leads/:id עם status:'converted', convertedToMembershipId (business-app.js:48408–48416).
חישובים
end_date = (startDate||now) + duration_days × 86400000ms → ISO date (server.js:29358). sessions_total = mtype.sessions. סכום התשלום ממולא אוטומטית במחיר הסוג בבחירת סוג (business-app.js:45165–45172) וניתן לעריכה.
מכונת מצבים
מצב התחלתי: active.
תופעות לוואי
תנועת הכנסה ב-transactions; כרטיס לקוח מאוחד; קישור member_business_links אם הטלפון שייך למשפחת WEFLOWZ.
ממשק
שדות: שם*, טלפון, אימייל, סוג מנוי*, סכום ששולם, אמצעי תשלום (cash/credit/transfer/app), תאריך התחלה (היום), ת"ז, תאריך לידה, מגדר, הערות (business-app.js:45108–45157, 48367–48380).
פערים
אין מניעת כפילות לפי טלפון. new Date(startDate) בחישוב הסיום מפורש כ-UTC — תאריך סיום מחושב במילישניות ולא בימים קלנדריים.
