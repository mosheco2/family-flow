לוגיסטיקה — תשתית, הרשאות ונתונים

אימות, gating מודול ויומן ביקורת לכל נתיבי /api/logistics

מטרה וטריגר
כל נתיבי /api/logistics/* (פרט ל-/api/logistics/track/:token ו-/api/logistics/track/:token/leave-at-door) עוברים את שרשרת ה-middleware verifyBizOrLegacy → requireModule('logistics') (server.js:32681–33482, 51 שימושים). הטריגר: כל קריאה מסביבת BIZ (business-app.js).
תנאים ואימותים
  • verifyBizOrLegacy (server.js:43056): אם יש header Authorization (עם או בלי Bearer ) — hash של הטוקן נבדק מול family_sessions.token_hash; טוקן לא קיים/פג תוקף → 401 'token לא תקף'; session_type !== 'biz' → 403 'נדרש token מסוג עסקי'; תקין → req.bizAuth = {groupId, userId, fromToken:true} ועדכון last_seen אסינכרוני (server.js:43063–43077).
  • בלי header כלל — fallback legacy: req.bizAuth = {groupId: req.body.groupId || req.query.groupId || null, userId:null, fromToken:false} ו-console.warn; הבקשה ממשיכה ללא אימות (server.js:43083–43087).
  • requireModule('logistics') (server.js:43126): legacy (fromToken=false) או ללא groupId → מעבר ללא בדיקה. אחרת קורא family_groups.managed_modules (cache בזיכרון 60 שניות, _MOD_CACHE_TTL=60000, server.js:43124). מערך ריק/NULL → מעבר ("עסק ותיק"). אם המערך לא כולל את המחרוזת 'logistics' → 403 'גישה למודול זה אינה כלולה בחבילה שלך'. שגיאת DB → fail-open.
  • אין אף בדיקת בעלות בנתיבי הלוגיסטיקה: :groupId בנתיב / group_id בגוף אינם מושווים ל-req.bizAuth.groupId, ונתיבי :id (עדכון/מחיקה) מבצעים WHERE id=$1 בלבד ללא סינון group (לדוגמה server.js:32795, 32835, 32873, 33363, 33479).
שלבי עיבוד
  1. middleware גלובלי של יומן ביקורת (server.js:121–144) נרשם ל-res.on('finish') לכל POST/PUT/PATCH/DELETE.
  2. אם status 2xx–3xx ו-req.bizAuth.groupId קיים ו-path לא בדילוג — logBizAction(groupId, userId, null, 'HTTP_'+method, 'route', path, ...) עם עד 12 שדות גוף, תוך סינון מפתחות password|token|secret|signature (server.js:129–139).
  3. דילוג מפורש לנתיבים /api/logistics/orders/\d+/status ו-/api/logistics/invoices/\d+/status (server.js:117–118) כי הם רושמים logBizAction ייעודי.
תופעות לוואי
כתיבה ל-biz_audit_log (server.js:4160–4168), fire-and-forget עם .catch(()=>{}).
ממשק
רוב קריאות הלוגיסטיקה ב-business-app.js (v1+v2: הזמנות, נהגים, רכבים, מחירון, COD, RFQ, מסלולים, מעקב, דוחות, נהג) נשלחות ב-fetch ללא header Authorization (למשל business-app.js:52508, 52697, 52780) ואין wrapper גלובלי ל-fetch ב-business.html / business-app.js. רק לקוחות וחשבוניות שולחים Authorization: Bearer ${window._bizToken} (business-app.js:53843, 54005, 54023, 54097, 54103) ו-_aiUpdateInvoiceStatus (business-app.js:57684).
פערים
  • בפועל כל נתיבי הלוגיסטיקה נגישים ללא טוקן (legacy) ולכל group/id — IDOR חוצה-דיירים מלא.
  • בקשות legacy אינן נרשמות ביומן הביקורת הגנרי (bizAuth.groupId null כי הלקוח לא שולח groupId בגוף/query, אלא group_id).
  • requireModule בודק את המחרוזת 'logistics', אך מזהי המודולים בקטלוג הלקוח הם מזהי טאבים (logistics_orders וכו', business-app.js:37532). אם managed_modules מכיל מזהי טאבים בלבד — קריאות עם טוקן (לקוחות/חשבוניות) יקבלו 403. התוכן המדויק של managed_modules לעסק לוגיסטיקה לא נקבע בקוד הנבדק.
