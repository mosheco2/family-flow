לוגיקה עסקית לבנייה מחדש. בכל תהליך מתועדים, לפי סדר: מטרה וטריגר, תנאים ואימותים, שלבי עיבוד (כולל סדר הכתיבות ל-DB), חישובים ונוסחאות, מכונת מצבים, תופעות לוואי (התראות, מטבעות, AI, cron), התנהגות הממשק, ולבסוף פערים. רוב התוכן מתאר את ההתנהגות כפי שהיא ממומשת. אימות והרשאות בנתיבי /api/store/* (verifyBizOrLegacy + requireModule)

מטרה וטריגר
כל נתיב חנות שמוגן ב-verifyBizOrLegacy (server.js:43056) ו-requireModule('sales') (server.js:43126). חלק גדול מנתיבי החנות אינם מוגנים בכלל (ראו "פערים").
תנאים ואימותים
  • אם יש כותרת Authorization (Bearer או גולמי): מחשבים hash, מחפשים ב-family_sessions; אם לא פג תוקף ו-session_type!=='biz' → 403 "נדרש token מסוג עסקי"; תקין → req.bizAuth={groupId,userId,fromToken:true} ועדכון last_seen אסינכרוני (server.js:43060-43075).
  • טוקן קיים אך לא נמצא/פג → 401 "token לא תקף" (server.js:43079).
  • ללא כותרת: fallback legacy — groupId נלקח מ-req.body.groupId או req.query.groupId, fromToken:false, נרשם warning (server.js:43082-43086).
  • requireModule: רק כש-fromToken=true; קורא family_groups.managed_modules עם cache של 60 שניות (_MOD_CACHE_TTL=60000, server.js:43124); מערך ריק/null → מעבר חופשי; מודול חסר → 403 "גישה למודול זה אינה כלולה בחבילה שלך"; שגיאה → fail-open (server.js:43126-43150).
ממשק
ממשק העסק (business-app.js) כמעט אף פעם לא שולח Authorization לנתיבי החנות — אין fetch-interceptor גלובלי (נבדק: אין window.fetch= ב-business-app.js/business.html). לכן כל הקריאות רצות ב-legacy ותלויות ב-groupId שבגוף/בשאילתה.
פערים
נתיבים שקוראים רק req.bizAuth.groupId ללא fallback לגוף, ושהלקוח קורא להם בלי groupId בגוף, נכשלים ב-400 "groupId נדרש": to-work-order (גוף {}, business-app.js:9666), prepare-send (ללא גוף, business-app.js:9600), PATCH /quotes/:id/status (גוף {quoteStatus} בלבד, business-app.js:9425), send-to-oneflow/link-only (גוף {familyGroupId}, business-app.js:9470, 12863, 12910). ראו תהליך הצעות המחיר.
